| Où | Défaut | Correctif |
| --- | --- | --- |
| Revue indépendante | `git init && git add . && git commit` laissait passer un `.env` | Refus des constructions invérifiables (D25) |
| Revue | `git add -f <ignoré> && git commit` non vu | Refusé, à lancer à part |
| Revue | Faux positifs : fichiers non suivis lus pour `-a`, tout l'arbre lu pour un seul `git add` | Lecture limitée aux chemins (D13) |
| Revue | Configuration Firebase bloquée | Règle Google levée pour ses trois fichiers (D24) |

| Contre-vérification | Régressions : `xargs git add`, accolades, gitleaks sur `git add <f>` ; `cd sub && git add -A` ; sous-shell | Corrigées (D26) |
| Scénario 8 | Commande composée (`\| tail`) refusée | « Une commande par appel » dans les deux skills |
| Scénario 8 | Checkpoint hors du commit de correctif | Inclus |
| Scénario 9 | Commentaire du gabarit réécrit par la copie | Ne cite plus les marqueurs |

## 4. Limites connues

- **secret-scan** :
  - sans gitleaks, ses motifs sont peu nombreux (un jeton Slack passe) ;
  - il ne voit que `git commit` ;
  - un fichier modifié sur la même ligne par une autre commande est lu dans son état d'avant ;
  - un binaire commité peut produire un faux positif.

  Détail : `docs/SECURITY.md`.
- **protect-sensitive** : il ne voit pas une écriture faite par Bash ; sans `jq`, il ne regarde que la racine de session.
- **En mode `-p`** : les écritures protégées et les `git push` soumis à une règle `ask` sont refusés. Les skills donnent alors la commande à lancer vous-même : c'est voulu, mais un scénario headless demande ces gestes manuels.
- **Non validé en session réelle** : la tâche `build` et le diagnostic d'une CI rouge par devops-engineer ; `gh pr edit` ; `issue`.
- **Non vérifié** : bash 3.2 (macOS) ; le préfixe `!` face aux hooks ; un gitleaks antérieur à 8.19.
- **Contexte des scénarios** : ils chargent aussi les plugins installés (`flutter-forge` 0.1.1, `plugin-dev`, `superpowers`).
